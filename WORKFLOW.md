# Project workflow

## 1. Explore unlabeled questions

Run `Rscript main.R`. The cached Stack Exchange CSV is used locally and is
never modified. The pipeline cleans the question text, builds TF-IDF/LSA
features, and compares k-means, DBSCAN, and sample-based hierarchical
clustering. Elbow, silhouette, cluster-size, density, and stability results are
exploratory diagnostics; none is diagnosis accuracy.

Review:

- `outputs/tables/04_algorithm_comparison.csv`
- `outputs/tables/04_kmeans_k_comparison.csv`
- `outputs/tables/04_dbscan_parameter_search.csv`
- `outputs/tables/04_cluster_summary_top_terms.csv`
- `data/processed/04_questions_with_clusters.csv`
- `data/processed/06_cluster_labeled_300_with_sources.csv`: balanced sample
  of 300 real Stack Exchange questions, with 15 assigned to each of the 20 current
  k-means clusters and the corresponding human-readable topic suggestion.
  Each row includes its original question ID, Gardening Stack Exchange
  permalink, source dataset filename, and creation time.
- `outputs/plots/`

The `cluster_id` and `cluster_label` in this sample describe unsupervised
groups, not 20 verified disease classes. `diagnosis_verified` is always false.
The sample is selected from the existing scraped questions, not generated
symptom records.

The source is the local input CSV at the project root (default:
`stackexchange_gardening_raw_25k.csv`; it contains 16,454 rows in this run).
Rows are original Gardening Stack Exchange questions; `source_url` links to
the individual post. The cluster assignment is generated by this project and
the topic label is a provisional summary, not an original Stack Exchange
diagnosis or an independently verified disease label. Check the source
platform's attribution and license requirements before redistributing question
text.

## 2. Name cluster topics, not diseases

Review `data/review/cluster_topic_labels.csv`. Each cluster row includes one
representative question ID and its symptom text, plus top terms and example
titles. Use these to write a concise `topic_label`, then record who reviewed it, the date,
and notes, and set `review_status` to `reviewed`. Otherwise the pipeline will
refresh the provisional suggestion on the next run. These labels describe themes in the questions (for example, leaf
discoloration or watering discussions). Do not use a cluster name as a
confirmed plant-health diagnosis or as a gold evaluation label.

For an independent human topic check, label every row in
`data/review/06_topic_blind_review.csv`. This sheet deliberately omits cluster
IDs and generated cluster labels. Read the title and question text, assign a
short consistent `human_topic_label` (or `unclear` if the text is insufficient),
and fill in reviewer/date. Do not look at the cluster-labeled file until all
human labels are complete. Existing review labels are preserved when the
pipeline is rerun. After completing the sheet, provide it for comparison with
the cluster assignments; agreement is a topic-coherence check, not disease
diagnostic accuracy.

Run `Rscript evaluate_topic_labels.R` after saving the completed sheet as
`data/review/06_topic_blind_review_reviewed.csv`. The script excludes those
reviewed question IDs from the corpus before fitting the vocabulary, TF-IDF,
SVD, choosing k, and training k-means. It then projects the reviewed questions
into the training-only feature space and compares their new cluster assignments
with your independent human topics. Outputs are saved as
`outputs/tables/08_holdout_topic_metrics.csv`,
`08_holdout_topic_predictions.csv`, and
`08_holdout_topic_crosstab.csv`.

Because training posts have no human topic labels and cluster IDs are arbitrary,
classification accuracy is not defined for this unsupervised holdout test.
Use adjusted Rand index (ARI) and normalized mutual information (NMI); cluster
purity is descriptive only. The earlier `07_topic_agreement_metrics.csv`
score used clusters fitted on the full corpus (including these reviewed rows),
so treat it as an in-sample comparison, not the independent holdout result.
For a requested, descriptive accuracy-like number, the script also maps each
holdout cluster to its most frequent human topic using those same 300 labels
and writes `08_posthoc_*` metrics and predictions. This reuses the test labels
to name clusters, so the resulting accuracy is optimistic and must not be
presented as independent test accuracy.
The evaluation script also appends/refreshes a `cluster_label` column in the
reviewed CSV with these post-hoc majority-topic predictions; the raw held-out
cluster number remains available in `08_holdout_topic_predictions.csv`.

The same command additionally trains a supervised **linear SVM** to predict
your `human_topic_label` values. It stratifies the reviewed records into an
80% training split and 20% test split, and fits vocabulary, TF-IDF, and SVD
using only the training portion. The SVM test accuracy and related metrics
are written to `outputs/tables/09_svm_topic_metrics.csv`, with test predictions,
per-topic metrics, and confusion matrix in the other `09_svm_*.csv` files.
This is the classification accuracy for your manually assigned topic labels;
it is not disease-diagnosis accuracy. If labels are edited, rerun the same
command to regenerate the test results.

The old `data/processed/05_manual_annotations_template.csv` is preserved, but
the new workflow does not use it as verified diagnostic data.

## 3. Build a source-linked verified case set

Add records to `data/verified/verified_plant_cases.csv`. Use one record per row:

| Column | Meaning |
|---|---|
| `case_id` | Unique local identifier |
| `symptom_text` | Short paraphrase of the documented symptoms; do not copy an article |
| `condition_label` | The condition explicitly supported by the source |
| `source_name` | Publisher or diagnostic institution |
| `source_url` | HTTPS URL that supports this case |
| `source_license` | Optional reuse/license note |
| `evidence_type` | `fact_sheet_paraphrase` or `confirmed_case` |
| `verified` | `yes` only after checking that the source supports the text and label |
| `verified_by` | Reviewer name or project role |
| `verified_on` | Review date in `YYYY-MM-DD` form |
| `review_notes` | Note whether this is only a fact-sheet paraphrase |

Prefer university extension services, university plant diagnostic clinics,
government agriculture agencies, and similarly accountable plant-health
institutions. Use pages that connect symptom descriptions to supported
conditions. A general fact sheet is not an individual diagnosed plant case.
Record the source URL for every row and respect its terms. The current file
contains 13 fact-sheet paraphrases, not 13 independently diagnosed plants.
Do not fabricate additional verified rows or mark guessed Stack Exchange
labels as source-verified. Do not mix `fact_sheet_paraphrase` and
`confirmed_case` rows in one run.

## 4. Calibrate clusters and measure performance

Rerun `Rscript main.R`. K-means and its text features are fitted only on the
unlabeled Stack Exchange questions. Verified-source examples are then projected
into this already-fitted feature space. Whole source pages are separated into
a calibration subset and a held-out test subset. Calibration labels alone
determine each cluster's most common condition; held-out labels are never used
to name clusters. Clusters without calibration examples remain unmapped, and
their test cases count as incorrect while also reducing mapped coverage.

This tests whether the Stack Exchange topic clusters can be associated with
the broad source-supported conditions. It is not a supervised diagnostic model:
the corpus cluster assignments are unlabeled, and the 13 fact-sheet paraphrases
are not independent plant observations. Report these metrics only as a tiny
source-derived benchmark, not real-world accuracy. To make evaluation useful,
collect many independently confirmed cases from numerous pages and institutions,
with enough source pages for both calibration and held-out testing. Review:

- `outputs/tables/06_cluster_condition_mapping.csv`: the calibration-only
  condition assigned to each cluster and the calibration counts/purity
- `outputs/tables/06_calibration_cases.csv`: the exact calibration cases,
  source pages, labels, and assigned clusters used to build that mapping
- `outputs/tables/06_classification_metrics.csv`: mapped test coverage,
  accuracy, balanced accuracy, and macro precision/recall/F1
- `outputs/tables/06_per_class_metrics.csv`: per-condition support and scores
- `outputs/tables/06_confusion_matrix.csv`
- `outputs/tables/06_test_predictions.csv`: held-out cases with their sources
- `outputs/tables/06_all_verified_case_predictions.csv`: predictions for all
  13 current verified-source rows, marked calibration or held-out
- `outputs/tables/06_all_verified_case_metrics.csv`: all-row apparent score.
  This includes calibration rows used to define the mapping and is not an
  independent estimate of model performance.
- `analysis_report.txt`

Accuracy alone can hide poor performance on rare conditions. Check mapped
coverage, per-class support, macro F1, confusion matrix, and source separation.
This is a text-only exploratory pipeline, not an image-based diagnostic tool.
Scores do not establish clinical diagnostic quality.

## 5. Predict a new question

After `outputs/models/06_verified_cluster_mapping.rds` exists, run
`run_prediction_check.bat` or:

```text
Rscript predict_new_question.R "My plant has yellow leaves and wilting"
```

The output is the condition mapped to the assigned cluster, or an explicit
unknown result if that cluster was not represented in calibration. It is not a
confirmed diagnosis.
